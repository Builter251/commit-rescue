Git 3분 개념

이 서비스의 모든 설명은 아래 5개 영역과 하나의 경계로 이야기합니다. 읽는 곳이 아니라 보는 곳입니다.

💻 내 컴퓨터 | ☁️ GitHub

git pull은 따로 그리지 않습니다. fetch + merge이기 때문입니다. 아래 버튼으로 두 화살표가 연달아 강조되는 것을 확인해보세요.

명령어를 누르면 어느 영역에서 어느 영역으로 움직이는지 표시됩니다.

꼭 가져가야 할 네 가지

  1. git commit은 GitHub에 아무것도 보내지 않습니다. 인터넷이 끊겨도 동작합니다. GitHub에 반영되는 것은 git push 뿐입니다.
  2. git add한 파일과 작업 폴더의 파일은 서로 다른 버전일 수 있습니다. 그래서 스테이징을 별도의 영역으로 봅니다.
  3. origin/main은 GitHub에 있는 것이 아니라 내 컴퓨터에 있습니다. 마지막으로 fetch했을 때 본 GitHub 상태를 적어둔 메모입니다. 동료가 push해도 내가 fetch하기 전까지 움직이지 않습니다.
  4. git fetch는 원격의 커밋을 실제로 받아와 origin/main을 갱신합니다. 다만 로컬 main과 작업 파일에는 자동으로 합치지 않습니다. 합치는 것은 merge이고, pull은 fetch + merge입니다.

시작할 때 한 번만 해두면 좋은 설정

git config --global init.defaultBranch main
git config --global push.autoSetupRemote true

두 번째 설정은 Git 2.37.0부터 쓸 수 있고, 첫 push에서 만나는 fatal: The current branch has no upstream branch 에러를 통째로 없애줍니다.

명령어 사전

알파벳순이 아니라 상황순입니다. 카드를 누르면 위쪽 5영역 다이어그램에서 그 명령이 건드리는 영역이 강조됩니다.

  • ✓ 안전

    지금 상태 확인

    git status

    영향 영역 없음 (조회만 합니다)

    무엇을 하든 여기서 시작합니다. 어떤 파일이 어느 영역에 있는지 한 번에 보여줍니다.

  • ✓ 안전

    커밋에 담을 파일 고르기

    git add <파일>

    영향 영역 작업 폴더 → 스테이징

    작업 폴더에서 10개를 고쳐도, add한 것만 커밋됩니다. 이 선택 단계가 Git과 단순 백업의 차이입니다.

  • ✓ 안전

    기록 남기기

    git commit -m "메시지"

    영향 영역 스테이징 → 로컬 main

    내 컴퓨터의 .git 폴더에만 기록됩니다. GitHub에는 아무것도 가지 않습니다.

  • ✓ 안전

    GitHub에 올리기

    git push

    영향 영역 로컬 main → GitHub main (+ origin/main 갱신)

    여기서 처음으로 인터넷이 필요합니다. 성공하면 origin/main 메모도 함께 최신이 됩니다.

  • ✓ 안전

    원격 정보 받아오기

    git fetch

    영향 영역 GitHub → 로컬 저장소 + origin/main

    “확인만 하는 명령”이 아닙니다. 원격의 커밋 객체를 실제로 내려받아 origin/main을 갱신합니다. 다만 로컬 main과 작업 파일은 건드리지 않으므로, 안심하고 자주 실행해도 됩니다.

  • ! 주의

    원격 내용 가져와 합치기

    git pull

    영향 영역 fetch 후 origin/main → 로컬 main → 작업 폴더

    fetch + merge입니다. 작업 폴더까지 바뀌므로 충돌이 날 수 있습니다. 먼저 git status로 정리된 상태인지 확인하세요.

  • ! 주의

    파일 수정 취소

    git restore <파일>

    영향 영역 스테이징 → 작업 폴더

    기본 소스는 HEAD가 아니라 index(스테이징 영역)입니다. 이 차이가 함정을 만듭니다.

    git add app.js를 한 뒤 git restore app.js를 실행하면 아무 일도 일어나지 않은 것처럼 보입니다. 스테이징에 이미 add한 내용이 들어 있고, restore는 거기서 가져오기 때문입니다.

    마지막 커밋 상태로 되돌리려면 git restore --source=HEAD -- app.js를 쓰세요.

  • ✓ 안전

    add 취소

    git restore --staged <파일>

    영향 영역 로컬 main(HEAD) → 스테이징

    스테이징에서만 내립니다. 작업 폴더의 수정 내용은 그대로 남습니다. 그래서 안전합니다.

  • ! 주의

    마지막 커밋 상태로 파일 되돌리기

    git restore --source=HEAD -- <파일>

    영향 영역 로컬 main(HEAD) → 작업 폴더

    커밋하지 않은 수정이 사라집니다. 되돌릴 수 없으니 git diff로 무엇이 사라지는지 먼저 보세요.

  • ✓ 안전

    브랜치 이동

    git switch <브랜치>

    영향 영역 로컬 저장소 → 스테이징 + 작업 폴더

    커밋하지 않은 수정이 있으면 Git이 이동을 막아줍니다. 새로 만들면서 이동하려면 git switch -c <브랜치>.

  • ! 주의

    직전 커밋 수정

    git commit --amend

    영향 영역 로컬 main

    기존 커밋을 고치는 것이 아니라 새 커밋으로 갈아끼웁니다. 해시가 바뀌므로 이미 push했다면 강제 푸시가 필요해집니다. 협업 중이라면 revert를 쓰세요.

  • ✓ 안전

    이미 올린 커밋 되돌리기

    git revert <해시>

    영향 영역 로컬 main (새 커밋 추가)

    기록을 지우지 않고 반대 내용의 커밋을 하나 더 쌓습니다. 그래서 동료의 작업을 망치지 않습니다. 이미 push한 것은 항상 이 방법입니다.

  • ✓ 안전

    브랜치 전환 없이 병행 작업

    git worktree add <경로> <브랜치>

    영향 영역 새 작업 폴더 생성

    같은 저장소를 다른 폴더에 동시에 펼쳐놓습니다. 기능 개발 중 급한 버그 수정이 들어왔을 때, 지금 작업을 커밋하지 않고 별도 폴더에서 고칠 수 있습니다.

    git worktree add ../프로젝트-hotfix hotfix
git worktree list
git worktree remove ../프로젝트-hotfix

    같은 브랜치를 두 worktree에서 동시에 열 수 없습니다. 이 제약을 모르면 에러 메시지를 이해할 수 없습니다.

    stash와의 차이 — stash는 한 폴더 안에서 작업을 잠시 치워두는 것이고, worktree는 폴더를 하나 더 만드는 것입니다. 에디터를 두 개 띄워 비교하며 작업할 수 있습니다.

로컬과 원격 비교하기

git log --oneline origin/main..main   # 내게는 있고 원격에 없는 커밋
git log --oneline main..origin/main   # 원격에는 있고 내게 없는 커밋

이 명령은 GitHub의 현재 상태가 아니라 마지막 fetch 결과와 비교합니다. 최신 상태로 비교하려면 git fetch를 먼저 실행하세요.

구식 / 신식 대응표

검색하면 대부분 checkout 기준의 옛날 답변이 나옵니다. 부정하지 말고, 같은 일을 한다는 것만 알아두세요.

구식 명령어와 현재 권장 명령어 대응표
하고 싶은 일권장 (현재)검색에서 자주 보이는 방식
스테이징 내용으로 파일 되돌리기git restore <파일>git checkout -- <파일>
add 취소git restore --staged <파일>git reset HEAD <파일>
브랜치 이동git switch <브랜치>git checkout <브랜치>
브랜치 생성 후 이동git switch -c <브랜치>git checkout -b <브랜치>
직전 브랜치로 돌아가기git switch -git checkout -

checkout 하나가 “브랜치 이동”과 “파일 되돌리기”라는 전혀 다른 일을 담당했던 것이 초보자 혼란의 큰 원인이었습니다. switch와 restore는 2019년 도입 후 오랫동안 실험적 상태였다가 2025년에 정식이 되었고, 그래서 기존 자료 대부분이 아직 checkout 기준으로 쓰여 있습니다.

git reflog는 어디까지 구해주나요

git reflog는 이동하거나 삭제된 커밋을 찾는 데 유용합니다.

다만 한 번도 커밋하지 않은 파일 변경까지 복구해주지는 않습니다.

그래서 위험한 명령 전에 먼저 커밋하거나 stash해두는 것이 중요합니다.

자주 하는 실수

이 서비스를 만들면서 제작자가 실제로 겪은 사고 기록입니다. 검색해도 잘 안 나오는 것들이라 남겨둡니다.

  1. 1. .env를 커밋해버렸다

    .gitignore를 만들기 전에 git add .를 먼저 했다. API 키가 들어 있는 파일이 그대로 올라갔다.

    배운 것 — 순서가 중요하다. 먼저 AI Studio에서 키를 폐기·재발급하고, 그다음 커밋 이력을 정리한다. 반대로 하면 정리하는 동안에도 유출된 키가 살아 있다. 그리고 git rm --cached .env는 앞으로의 커밋에서만 빼줄 뿐, 이미 올라간 과거 커밋에는 그대로 남는다.

  2. 2. 첫 push에서 upstream 에러

    fatal: The current branch main has no upstream branch. 브랜치는 있는데 “어느 원격의 어느 브랜치에 올릴지”를 정해준 적이 없어서 생기는 에러였다.

    배운 것 — git push -u origin main으로 한 번 연결하거나, git config --global push.autoSetupRemote true를 한 번만 설정하면 다시는 만나지 않는다.

  3. 3. git add 후 git restore를 했는데 아무 일도 안 일어났다

    수정을 되돌리려고 git restore app.js를 실행했는데 파일이 그대로였다. 버그인 줄 알았지만 아니었다.

    배운 것 — restore의 기본 소스는 HEAD가 아니라 index다. 이미 add해둔 내용을 다시 덮어쓴 것이라 “그대로”로 보였다. 마지막 커밋 상태로 돌리려면 git restore --source=HEAD -- app.js. 이 사고 때문에 기획서의 영향 영역 표를 전부 다시 검토했다.

  4. 4. 로컬에서는 되는데 배포하면 안 된다

    로컬에서는 AI 응답이 잘 왔는데 배포본에서는 500이 떴다. .env는 .gitignore에 있으니 배포 서버에는 애초에 존재하지 않는다는 것을 잊고 있었다.

    배운 것 — Vercel의 Environment Variables에 키를 따로 넣어야 한다. 재미있게도 이건 이 서비스가 설명하는 문제와 같은 구조다. “내 컴퓨터에 있는 것”과 “서버에 있는 것”은 다르다. commit이 GitHub에 아무것도 보내지 않는 것과 똑같은 이야기다.

  5. 5. fetch했는데 파일이 안 바뀌어서 또 fetch했다

    동료가 push했다길래 git fetch를 했는데 내 파일이 그대로였다. 몇 번을 더 했다.

    배운 것 — fetch는 커밋을 받아와 origin/main을 갱신할 뿐, 로컬 main과 작업 폴더에는 합치지 않는다. 합치려면 git merge origin/main이 필요하고, git pull은 이 둘을 한 번에 하는 것이다. 이 경험이 5영역 모델을 만든 이유다.
